PART 2 · DATA SPECIFICATION

平台不是 UI 專案；
告警事件資料模型才是公司資產

映射表應獨立維護；新增廠牌不需改動規則引擎。

標準化告警碼可攜資料資產
alarm_uid｜全平台唯一識別
source_system／site_id｜來源與案場
device_id／type／model｜設備與備品脈絡
raw_alarm_code｜原廠碼原值保留
norm_alarm_code｜跨廠牌標準碼
severity／alarm_desc｜分級與中文描述
start／end time｜含時區的事件生命週期
status／duration_sec｜狀態與派工門檻
measured／threshold｜門檻型告警判斷
parent_alarm_uid｜根因與子告警
rule_version｜開單規則版本
wo_id｜工單關聯
標準碼建議採三段式：設備類型．故障域．具體現象，例如 INV.THERMAL.OVERTEMP。
資料來源：規格書 §1.4.1–1.4.2。兩案文件均未列實際欄位，本頁為業主規格補位。4 / 10
PART 2 · AUTOMATION GUARDRAILS

沒有三個必要機制，
自動派工只會把噪音放大成現場成本

這些是規則引擎的基本護欄，而不是儀表板的呈現功能。

上線風險可調參數
①

去抖動／去重

同設備＋同標準碼，在冷卻期 X 分鐘內只開一張；持續 Y 分鐘才觸發。X／Y 須由使用單位調整。

②

父子告警抑制

以案場→併網點→變流器→組串的階層，抑制下游開單，保留紀錄並關聯根因。

③

靜默失效偵測

「沒有資料」不是告警；以預期回報週期 N 倍偵測資料新鮮度，產生系統級離線告警。

儀表板呈現 ≠ 主動偵測與開單

GW／設備在線畫面只是呈現；規格要求的是一條與告警串流平行的偵測路徑。

每張工單記錄 rule_version

沒有版本欄位，規則調整後無法判斷成效來自調參還是季節變化。

資料來源：規格書 §1.4.3–1.4.4。三項機制為業主新增要求，森淨兩份提案均未涵蓋。5 / 10

PART 3 · INTEGRATION OPTIONS

平台吸收派工，
或 API 切分邊界？

本文傾向 A；它的組織成本最高，但守住資料主權與單一維運歷史。

A 本文傾向C 不建議
A

平台吸收派工

PV 戰情平台為唯一主體；RD 派工併為模組，既有系統退場或降為唯讀歸檔。

長期：單一資料源、單一維運歷史、資料主權完整。代價：現場重訓與既有系統調整。
B

明確切分邊界

平台做告警正規化與巡檢；既有系統做工單生命週期，以 API 串接。

優點：保留既有投資。代價：介面長期維護、跨系統 KPI 易對不上。
C

平行推進，六個月後收斂

兩案各自進行，暫不決策。

不建議：既成事實形成後，規則衝突與整併成本遠高於現在。

PART 3 · EXPECTATION GAP

森淨第一階段解決的是
「判讀介面分散」，不是「判讀需要人」

這個期待落差必須在整合決策時講清楚，否則平台上線後，使用單位仍會認為問題沒解決。

Phase 1 人工判讀不得誤列交付

RD 想解決的痛點

  • 告警進入派工後，仍需要人工判讀
  • 期待降低人工判斷與現場無效出勤
  • 趨勢分析列為事前工作線

森淨 Phase 1 的實際交付

  • 警報正規化、三級分級、任務建立與回報
  • 改善工程師在多套系統間切換
  • AI 故障預測明確置於 Phase 3
規則演進的正確路徑：A. 原廠手冊打底 → B. 資深工程師校正 → C. 歷史工單回推。 C 的前提是完整的告警與工單資料先到位。
資料來源：規格書 §2.3、FAQ Q3。森淨「減少 70% 系統切換與巡檢時間」屬廠商宣稱，未見計算依據。8 / 10
PART 4 · FOUR-QUESTION TEST

以使用部門四題檢驗：
只有第一題被部分回答

兩份廠商提案與一份內部 kickoff，未回答「資料欄位長什麼樣」這個決定成敗的問題。

完整性是咽喉依序成熟
① COVERAGE

涵蓋率

有來源分佈與介接手段；缺設備層級與未納入卡點。

② COMPLETENESS

完整性

兩案皆未列實際欄位，是全案咽喉。

③ AUTOMATION

判讀自動化

平台 Phase 1 仍人工判讀；RD 無時程。

④ LEARNING

回饋學習

都有留痕／查詢，沒有分類、版本與假陰性機制。

檢驗題森淨提案RD 派工本規格補位
① 涵蓋率◐ 部分回答✕來源佔比、設備顆粒度、90% 驗收範圍
② 完整性✕ 有口號無欄位✕告警事件模型、標準碼映射表
③ 自動化✕ Phase 3 才 AI◐ 無時程可調規則、三機制、版本
④ 學習◐ 查詢非優化✕分類、precision／recall、人工開單
