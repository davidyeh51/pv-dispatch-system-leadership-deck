04 · DATA SPECIFICATION

平台不是 UI 專案；告警事件資料模型才是可累積的公司資產

alarm_uid｜全平台唯一識別
source_system／site_id｜來源與案場
device_id／type／model｜設備與備品脈絡
raw_alarm_code｜原廠碼原值保留
norm_alarm_code｜跨廠牌標準碼
severity／alarm_desc｜分級與中文描述
start／end time｜含時區的生命週期
status／duration_sec｜狀態與派工門檻
measured／threshold｜門檻類告警判斷
parent_alarm_uid｜根因與子告警
rule_version｜開單規則版本
wo_id｜工單關聯
標準碼採三段式：設備類型．故障域．具體現象（例：INV.THERMAL.OVERTEMP）。映射表應獨立維護；新增廠牌不需改規則引擎。

資料來源：規格書 §1.4.1–1.4.2。本頁是業主規格補位；兩案文件均未列實際欄位。

05
05 · AUTOMATION GUARDRAILS

沒有這三個機制，自動派工會把噪音放大成現場成本

①

去抖動／去重

同設備＋同標準碼，在冷卻期 X 分鐘內只開一張；持續 Y 分鐘才觸發。X／Y 須可由使用單位調整。

②

父子告警抑制

以案場→併網點→變流器→組串的設備階層，抑制下游開單，保留紀錄並關聯根因。

③

靜默失效偵測

「沒有資料」不是告警；以預期回報週期 N 倍偵測資料新鮮度，產生系統級離線告警。

DISTINCTION

儀表板呈現 ≠ 主動偵測與開單

GW／設備在線畫面只是呈現；規格要求的是與告警串流平行的偵測路徑。

GOVERNANCE

每張工單記錄 rule_version

沒有版本欄位，規則調整後無法判斷成效來自調參還是季節變化。

資料來源：規格書 §1.4.3–1.4.4。三項機制為業主新增要求，森淨兩份提案均未涵蓋。

07 · INTEGRATION DECISION

三個整合選項：本文建議 A，但需跨部門拍板

A

平台吸收派工

PV 戰情平台為唯一主體；RD 派工併為模組，既有系統退場或降為唯讀歸檔。

長期：單一資料源、單一維運歷史、資料主權完整。
代價：現場重訓、既有系統調整、RD 主導權改為參與權。
B

明確切分邊界

平台做告警正規化與巡檢；既有系統做工單生命週期，以 API 串接。

優點：保留既有投資與使用習慣。
代價：介面長期維護、跨系統 KPI 易對不上。
C

平行推進，六個月後收斂

兩案各自進行，暫不決策。

不建議：既成事實形成後，規則衝突與整併成本遠高於現在。
A 的組織成本最高，但守住本案最大長期價值：資料主權＋單一維運歷史。 決策應由 3.4 研發與 4.6 運維共同上呈。

資料來源：規格書 §2.4。A 為本文傾向，尚非已核定決議。

09 · ACCEPTANCE, NOT SLOGANS

第一階段驗收不綁「流程跑通」；綁資料完整度與規則可運作性

前三名來源必要欄位填充率 ≥ 95%
Top 50 高頻告警碼完成標準化映射
去抖動、父子抑制、心跳偵測皆可運作
規則參數可由使用單位自行調整
連續 30 天自動開單 precision 達議定門檻
人工開單永久可用，假陰性可統計
無廠商協助完成一次全量資料匯出
資料模型、映射表、API 文件簽收
KPI 必須有公式：PR、能量可用率、MTTA、MTTR、precision 與 recall。只優化誤報會讓規則過度保守；人工開單與「系統未偵測」標記不可取消。

資料來源：規格書 §1.7、§1.9。precision 門檻待雙方議定，其餘為建議驗收要求。
